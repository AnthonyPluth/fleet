# The agent review

How `.github/workflows/agent-review.yml` (`workflow_call`) reviews an agent's pull request, what it trusts, how a re-review and a carried-forward verdict work, and what the pieces in `fleet_tools/agent_review.py` decide. The caller snippet and the inputs are in [adopting.md](adopting.md); where Waypoint and Runway differed is in [drift.md](drift.md).

## The default policy

By default (the owner's policy) Codex reviews every pull request and the Claude review runs only on security-sensitive ones:

- **`first-review` is `false`**: no independent "Agent review", no comment, no status.
- **The second review still runs** on a risky pull request (a label in `second-review-labels`, `safety-critical,security` by default, or a changed path in `second-review-paths` or `second-review-always`), and passes any other with "Not a risky pull request" ([below](#the-second-review)).
- **The merge gate requires "Second review" alone** (`required-statuses`' default) and fails on a blocking second-review finding (its status fails) and on any open review thread from Codex with a P1 or P2 badge (`blocking-thread-badges`, `blocking-thread-authors`), whether or not the second review ran. `require-codex-review: true` also makes the gate wait for Codex's review of the head commit ([adopting.md](adopting.md#merge-gate)).

An app that wants the first review back passes `first-review: true` to `agent-review.yml` and lists `Agent review` in the gate's `required-statuses` (with `Second review`). Everything below describes the first review for that case; the second review is the same either way.

## Two jobs

`review` holds the secret and reads the code. It checks out fleet at the pinned ref (`.fleet/`: the prompt, the schema of the answer, the locked Claude Code, `agent-review-run.sh`, `agent_review.py` and the stub reviewer the self-test uses) and the caller's base commit (`trusted/`: `AGENTS.md` and `.github/agent-review/context.md`), decides whether this pull request and this event get a review, reads the last review's comment, checks out the pull request's head to read only (`review/pr`, `persist-credentials: false`), gathers the change and runs the reviewer in `review/`. Nothing from the pull request is run, built, installed or imported: `git` reads the checkout with `--no-ext-diff --no-textconv` and the tools run as `python3 -I .fleet/...`. The secrets appear only in the Review step's `env`, and that step runs only fleet's script.

`report` holds the write token and never sees the code or the secrets; it checks out fleet's tools alone, for the finding outcomes. It posts the one comment (updated by each review; the marker is its first line), the "Agent review" status on the head commit and starts the caller's merge gate (`merge-gate-workflow`), which a status change doesn't start by itself. With `dry-run: true` it prints each of those instead. A `skip` verdict posts nothing.

Both run on `ubuntu-latest` (`# hosted:`): the review job reads untrusted content with secrets in reach, the report job holds the write token, and neither should land on an app's own runner.

## Who and when

- An **agent's pull request** is one whose commits carry a `Claude-Session` or a Claude `Co-Authored-By` trailer, or whose description says Claude Code generated it (`is_agent`). Anyone else's gets a passing status, "Not an agent's pull request". Dependabot's gets none (the merge gate doesn't ask for one on its pull requests).
- A pull request **from a fork** isn't reviewed (that would spend the secret on anyone's code): an agent's from a fork gets an `error` status, for a maintainer to push it to a branch of the repository.
- A consumer **without `.github/agent-review/context.md`** on main gets an `error` status that names the file.
- **`ready_for_review`** reviews only when the head has no "Agent review" status set by the workflow yet (`wanted`): a draft is reviewed on each push like any pull request, and marking it ready doesn't pay for it twice.
- **`labeled` and `unlabeled`** run no first review: the review job's `if:` keeps them out, and the concurrency group (`agent-review-<pr>-<fake-review>`, the last part empty outside the self-test, `cancel-in-progress`) is the job's, not the workflow's, so a label event can't cancel a running review. Only the second review (`FLEET-SECOND-REVIEW`) reacts to labels.
- **`first-review: false`** (the default) runs neither job: no status, no comment. `true` runs both.

## The re-review and the carried verdict

The comment's hidden lines record what a review was: line 1 the marker `<!-- agent-review -->`, line 2 `<!-- agent-review-state sha=<head> verdict=pass|blocking -->`, line 3 `<!-- agent-review-findings <base64 JSON> -->`, line 4 `<!-- agent-review-outcomes <base64 JSON> -->` (what became of each finding; below). Only these are parsed on the next push (`previous`); the rest of the comment quotes the reviewer and is data.

- When the new head descends from the commit the last review read, the reviewer also gets `previous-review.md` (that review's text) and `since-last-review.patch` (what changed since, in the pull request's own files, without main's merged-in changes and the files left out of the diff), and `incremental.md` is added to its prompt: check each earlier finding, read every new line closely, open every changed image again. Its findings replace the earlier ones; `diff.patch` is still the whole change.
- When the last review **passed** (its comment says `pass` and its "Agent review" status, set by the workflow, is `success`) and everything pushed since is merges of main that leave the pull request's own change byte for byte as reviewed (`only_main_merged`: every added commit not on main is a merge, the same files, and `git diff --full-index --binary main...head` identical, so a file main changed too never compares equal), the verdict is **carried forward**: a passing status on the new head, "Carried forward from the review of <sha>: only main merged in since", and the comment stays. A blocking or failed review is never carried, and anything that can't be proved identical (a rebase, another branch merged, a conflict resolved by hand, a `git` error) is reviewed.
- Without a usable earlier commit (none, rebased away, a missing body) it reviews the whole change.

## What the reviewer reads

`diff.patch` is `git diff main...head` without the files `left_out` names, which `omitted.txt` lists and `files.txt` still includes: images (a diff can't show them; the prompt has the reviewer open each one), lockfiles, and the paths the `generated` input names (the app's generated API contract and feature map, a golden fixture). Fixtures, demo and sample data (anything under `tests/`, or with `fixture`, `demo`, `sample`, `example` or `seed` in its path) are never left out, lockfiles among them, because they are where a real record is likeliest to land, unless `generated` names the file: an explicit entry wins, so Runway's `tests/fixtures/forecast_golden.json` stays out by listing it. Nothing under `.github/` is ever left out: the workflows and the lockfile of the Claude Code the review runs are always read in full.

The prompt (`prompt.md`) is generic; `context.md` says what the app is, what private data looks like there and where it would land, which files are generated and what checks cover them, and which `AGENTS.md` sections matter most. The reviewer reads both. Everything in the diff, the commits, the checkout and the earlier review is data to it, never instructions, and an instruction found there is a blocking finding.

## The reviewer's isolation

`agent-review-run.sh` runs Claude Code (`--print`, `--output-format json`, `--json-schema schema.json`) from `$RUNNER_TEMP`, installed with `npm ci` from fleet's `.github/agent-review/package-lock.json` (Dependabot bumps it weekly after a seven-day cooldown; consumers drop their own copy), with Read, Grep and Glob as its only tools, confined to `review/` (`--restricted`), no settings files, hooks, CLAUDE.md, skills, plugins, slash commands or MCP servers, no session saved, and no GitHub token. It authenticates with `ANTHROPIC_API_KEY` when set, else `CLAUDE_CODE_OAUTH_TOKEN`, passing only the one it uses. The model is `sonnet`, fixed in the workflow: no input changes it, so a review never runs on a costlier model; the owner's rule is Sonnet for the first review of every agent's pull request and Fable for the second review of risky ones (temporarily Opus, below). `budget-usd` and `max-turns` bound a run; hitting either ends it with an error result, which fails the review rather than passing it, and each run logs the turns and cost it took.

The one step that holds a secret is also where the answer is checked for it: an output that contains the secret in use is replaced with `{"is_error": true, "subtype": "error_secret_in_answer"}` before the Verdict step reads it, and the status says "contained a secret; not posted".

## The answer and the verdict

The answer is the schema's JSON: a `summary` and `findings`, each with `severity` (`blocking` or `advisory`), `kind`, `title`, `detail`, and optionally `check`, `file` and `line`. `kind` is the bold title of the item under `AGENTS.md`'s "Mistakes that keep coming back" the finding falls under, verbatim, or `other`; `check` names the lint rule, Semgrep rule, type check or test that would have caught it. `report` turns the output into the verdict: a blocking finding is `blocking` (the status fails), none is `pass`, and anything else is `error` and never a pass: unreadable output, a reply that isn't the schema's JSON (one in a ```` ```json ```` block of the reply text is accepted), a finding without a kind, a limit hit, an error result, or an answer that quotes a secret.


The comment is built from the findings (`render`), with every piece of the reviewer's text defused: `@` can't mention anyone and `<!--` can't forge a hidden line. Line 3 carries the findings as data for the monthly mining of repeated findings (`FLEET-MINING`): `id`, `severity`, `kind`, `title` (defused, cut to 200 characters), `file` and `check` per finding, base64 JSON, at most 8 KB (findings are dropped from the end to fit; the outcomes record below is merged from the review job's complete `findings` output, never from this cut line). `fleet review-mine` reads that line and nothing else of the comment ([review-mining.md](review-mining.md)).

## Finding ids, outcomes and `/fleet dismiss`

Nothing in a review's verdict says what happened to a finding afterwards, yet that is the best signal for improving the reviewer: a kind that keeps getting fixed is a real mistake and should become a check, a kind that keeps getting dismissed means the reviewer over-flags. The outcomes record collects both, deterministically, without changing how a verdict is reached (`FLEET-FINDING-OUTCOMES`; the reports built on it are `FLEET-MINING-SIGNALS` and `FLEET-LOOP-STATS`).

- **The id.** Every finding has one: the first 8 hex digits of SHA-256 over its `kind`, its `file` (empty when none) and its title, joined by newlines, the title lowercased with punctuation and symbols removed and whitespace collapsed (`finding_id`). So "Drops rows!" and "drops  rows" in one file share an id, and the same title in another file has a different one. The comment shows it after the title as `` `f:1a2b3c4d` ``, and the line-3 findings record carries it as `id` (readers treat it as optional).
- **The outcomes record** is line 4 of the comment, `<!-- agent-review-outcomes <base64 JSON> -->` (the second review writes its own, `<!-- second-review-outcomes … -->`, under its marker): a list of entries with `id`, `status` (`open` or `resolved`), `kind`, `file`, `title`, `first` (the commit the finding was first seen at) and, when resolved, `resolved` (the commit that no longer had it). The report job merges it (`fleet_tools/review_outcomes.py`, from fleet's checkout): it reads only line 4 of the workflow's own previous comment (same marker, author `github-actions[bot]`), then an id this review reports is `open`, keeping its first-seen commit; a previously open id missing from this review becomes `resolved` with this commit when this was a full review, or an incremental one whose diff since the last review touched the finding's file (`plan`'s `touched` output, which counts every file of the pull request, images, lockfiles and generated files included), and otherwise stays `open`; a `resolved` id that comes back is `open` again. At most 200 entries and 16 KB: when over, the oldest `resolved` entries are dropped first. A finding's text in the record is defused like everything else quoted from the reviewer, and the whole comment stays under GitHub's size limit with every line at its cap.
- **Dismissals.** The owner records that a finding was wrong with a pull request conversation comment whose first line is `/fleet dismiss f:<id> <reason>`, with at least 10 characters of reason after trimming. Only a comment whose `author_association` is `OWNER` counts: `MEMBER`, `COLLABORATOR`, `CONTRIBUTOR` and `NONE` are ignored, as are an unknown id and a malformed command. The shared reader (`review_outcomes.load(repo, pr, marker)`) merges the record with the dismissals in comment order: a matching id becomes `dismissed`, with the reason (defused as `render` defuses the reviewer's text, at most 300 characters) and the comment's URL. Dismissals aren't written into the record, so a forged outcomes line inside a dismissal comment, or in a finding's title, changes nothing: the record is read from one place only.
- **A dismissal is a record, not an override.** It never changes "Agent review", "Second review" or the merge gate: a blocking finding still blocks until a push clears it, and the reviewer isn't told the reasons (`previous-review.md` leaves the Outcomes section out). The comment shows a dismissed finding as dismissed, with its reason and a link to the comment, under "### Outcomes", beside the findings resolved since the first review.
- **Reading it**: `fleet review-outcomes --repo OWNER/NAME --pr N [--json] [--second]` prints the merged outcomes (one line per finding, or JSON), for debugging and for the later reports.

## The second review

Risky pull requests are reviewed a second time, by a different model, as the `second-review` job and its `second-report` job in the same workflow (`FLEET-SECOND-REVIEW`). The owner's rule: the first review, where an app turns it on, stays Sonnet for every agent's pull request; the second runs on `claude-opus-5-5`, fixed in the workflow like the first (no input changes it). This is a TEMPORARY owner exception while Fable is rate-limited: the second review's model is normally `claude-fable-5-1`. Reverting means restoring `claude-fable-5-1` in `.github/workflows/agent-review.yml` (both `MODEL:` lines of the `second-review` job and its three comments), `tests/test_agent_review_workflow.py`, `tests/test_agent_review_risky.py`, `.github/agent-review/invariants.md` item 7, `docs/agent-review.md`, `docs/adopting.md`, `docs/drift.md` and `CHANGELOG.md`, or reverting this change's pull request. Its status is "Second review", its comment is its own (marker `<!-- second-review -->`, state line `<!-- second-review-state … -->`, findings line `<!-- second-review-findings … -->`), and the re-review and the carried-forward verdict are the first review's logic, parametrized by marker and status context (`agent_review.py second …`). The two reviews run in parallel and neither waits for the other; a finding in one fails only its own status. The second review doesn't need the first: with `first-review: false` it reads no `first-review.md`.

- **Risky** (`agent_review.py risky`, from the pull request's labels and `files.txt`) when either holds: a label in `second-review-labels` (default `safety-critical,security`), or a changed path matching a glob in `second-review-paths` (one per line; `**` spans directories; a renamed file counts by its old and its new name). `.github/**` and `.claude/**` always count. The comment says which ("Reviewed a second time because the pull request is labelled `security`; changes `.github/workflows/ci.yml` (matches `.github/**`)").
- **Not risky** is a passing "Second review" saying "Not a risky pull request", with no comment, so a merge gate can require the status on every pull request (`FLEET-MERGE-GATE`'s default). Not an agent's pull request, a fork, a missing `context.md`: as for the first review. Dependabot's pull requests get no status.
- **Label events.** `labeled` and `unlabeled` run only this job (the first review's `if:` keeps them out). An `unlabeled` event sent by anyone but the repository owner (`github.event.sender.login != github.repository_owner`) changes nothing: the job doesn't run (its `if:`), and `wanted` refuses it too, so the status stays as it was. The owner's removal re-evaluates the pull request. A label that isn't one of the trigger labels is a skip (nothing posted), and so is a label event on a head that already has a real "Second review" verdict (not the "Not a risky" pass, not an error): that review stands. Because a head reviewed before the label came may already carry a passing "Second review" and a passing "Merge gate", a label event that will run a review first goes through the `second-pending` job, which sets "Second review" to `pending` on the head and starts the merge gate again, so the pull request can't merge on the old status while the review runs; `second-report` replaces it with the verdict (an error or a failed job included). Only the newest "Second review" status the workflow set on the head counts as its verdict (`reviewed_here`): after a real verdict, the owner's removing the last trigger label posts a newer "Not a risky" pass, and re-adding the label reviews again. The job's concurrency group tells label events apart from pushes (`second-review-<pr>-<fake-review>-<fake-event>-label|push`), so a label event can't cancel a running review of a push; two label events replace each other.
- **Which run decides.** Two runs can review the same head: a push and a trigger label (or the owner's removal of one) start runs in different concurrency groups, so neither cancels the other, and both write the one "Second review" status and the one comment. GitHub shows the newest write, so on its own the run that *finished* last would win, and a push run's success finishing after a label run's blocking verdict would let the gate pass over it. Instead the verdict is decided from every run's verdict on the head, whichever finishes first (`decide` in `agent_review.py`):
  - **The run that started last decides** (runs are ordered by `github.run_id`, which GitHub hands out as the events come in; a re-run keeps its run's id), **except that a complete review's blocking verdict stands over a later pass**: when the latest run passed and an earlier run on the same head blocked, the head stays failed. The one later pass that clears it is "Not a risky pull request", which on the same head only comes after the owner removed the trigger label (the owner's decision, as before). A later run's error or pending isn't replaced by an earlier run's pass either.
  - **Which statuses count.** Each status the workflow posts names its run in its `target_url` (`<server>/<repository>/actions/runs/<id>`), and the comment's state line ends with ` run=<id>` (a line without it still parses, as run 0). A run id counts only after the workflow looks it up (`GET repos/<repository>/actions/runs/<id>`, `second runs` lists them) and finds a run of **the same workflow file, for the same event, for this pull request and this head** as the run looking (`trusted`). Anything else, whether a status from another workflow, a link to another host or repository, an id that doesn't exist, a run of another pull request or head, or a lookup that fails, counts for nothing: it never stops a run from posting its verdict and comment. A label run whose run has completed with its status still pending (it was cancelled) counts for nothing, so the next verdict on the head clears it.
  - **Before writing**, `second-report` and `second-pending` read the head's statuses and the comment, look the runs up and ask `second publish` what to post: their own verdict when it is the decided one or a blocking one (a blocking verdict is always recorded, so that a later pass can't lose it); the earlier blocking verdict, under their own link and prefixed "An earlier run's blocking verdict stands", when they are the latest run and passed; otherwise nothing (no comment, no status, no merge-gate start). The comment is written only with the run's own verdict, and it isn't replaced when a later trusted run wrote it for a newer head, or for this head with the verdict that decides.
  - **After writing its status**, a run reads the head again (up to three times) and, when the newest "Second review" status (anyone's) isn't the decided one, posts the decided one again (`second settle`, with its run's link and `#restored`). This covers a run that wrote between another's check and its post, and a forged status posted before that point. A restored copy counts as the run it names but never stands for that run's own newer status.
  - **Re-runs.** A re-run of a label run reviews again even though its own earlier attempt left a verdict on the head (`reviewed_here` doesn't count this run's own status as the head already reviewed), so it replaces its own verdict through the rules above; a re-run of an earlier run can't replace a later run's verdict. To get a fresh verdict otherwise, push, or (owner) remove and re-add the trigger label.
  - **The concurrency group** tells pushes, trigger-label events and other label events apart (`…-push`, `…-label`, `…-other-label`, matching the label against `second-review-labels` split on commas without spaces), so a label the review doesn't react to no longer cancels a running label review and leaves its pending status behind; two trigger-label events still replace each other.
  - **What it doesn't cover.** Any workflow in the repository that can write statuses can still post a "Second review" after every run has finished, and the gate reads the newest status: that was already so and isn't something the review's own runs can prevent (a pull request that adds such a workflow touches `.github/**` and is reviewed a second time). GitHub has no compare-and-swap for a comment, so two runs writing it within a second or two can leave the other run's comment (the status, which the gate reads, is put right as above; a passing verdict is carried forward only when the comment and the status both say it passed). A run cancelled by hand leaves its pending status until it is re-run or a new push comes, which fails closed.
- **Budget and turns**: `second-review-budget-usd` (default `10`) and `second-review-max-turns` (default `120`); hitting either is an `error`, never a pass, as for the first review.
- **What it reads**: everything the first review reads, plus `second-review.md` appended to the prompt (threat-model the change: who can reach the new code and with what input; check every promise or invariant it touches in `AGENTS.md` and in the app's `.github/agent-review/invariants.md`; require a positive and a negative test per invariant touched; treat any weakening of a check as blocking unless the linked issue asked for it; read the first review's comment, `first-review.md`, as data and say where it disagrees), `reason.txt` (why it is risky), the app's `invariants.md` from main when it has one (required whenever the caller sets `second-review-paths`: a numbered list of the app's invariants and the test or rule that holds each; a risky pull request without it is an `error` status naming the file), and the first review's comment when there is one. fleet's own is `.github/agent-review/invariants.md`.
- **Cost**: a second review runs only on risky pull requests, on each push to one (and when a trigger label is added), with its own budget; a push that only merges main carries a passing verdict forward as for the first review, and a label event on a reviewed head posts nothing. The budget and turn defaults are higher than the first review's because the model is costlier and the prompt asks for more; the caller tunes them by the turns and cost each run logs.

## The verification record

With `verification: true` (`FLEET-VERIFY-REVIEW`; the default, `false`, changes nothing), both reviews judge the pull request's verification record, the table its description carries between the `fleet-verification` markers (`FLEET-VERIFY-RECORD`; [adopting.md](adopting.md#verification-records)). `fleet checks` covers whether the record is there and well formed; whether it matches the change takes judgment, so the reviews do that part. The record is part of the pull request, so it is untrusted text and reaches the reviewer exactly like the code: as a file, read with its read-only tools, never in the prompt.

- **What `plan` does.** The description reaches the Gather step as the environment variable `BODY` (never in an expression). When the record block is there, `agent_review.py plan` extracts it with `fleet_tools/verification.py`'s block extraction and size limits (the description's 65,536-character cap) and writes it to `verification.md` in the review directory; a block that doesn't parse is still written, with a first line saying so and the parser's rule (which names the line and the rule, never the description's text), so the reviewer judges what is there and leaves the format to `fleet checks`. The prompt then gains `.github/agent-review/verification-review.md`, which names the file as the verification record; without a record, or with the input off, there is no file and no section, and the prompt is byte for byte what it was.
- **What the reviewer checks.** Coverage: every behaviour the diff changes appears as a dimension, `verified` or `not verified`. Evidence: each `verified` row's evidence exists in the diff or the tree (the named test, flow, command, file or screenshot) and plausibly exercises the change. Gaps: each `not verified` row says why and what would close the gap. A `verified` claim whose evidence doesn't exist, or a changed behaviour missing from the record, is blocking; a vague gap reason is advisory. The findings' `kind` is **Verification that doesn't cover the change**, the shared `mistakes` item (partly checked: `fleet checks verification`; coverage is judged by the review), so the monthly mining counts them like any other kind. The second review adds (`second-review.md`): each invariant or promise the change touches must appear as a dimension, `verified` with the positive and negative tests it already requires, or `not verified` with a reason; anything else is blocking.
- **The re-review.** The comment's state line carries a hash of the record the review read (`<!-- agent-review-state sha=<head> verdict=pass|blocking record=<16 hex> -->`, the suffix absent when there was none; a state line without it still parses). `plan` compares the hash of the record at the new head with the last review's (`PREV_RECORD`, read by `previous`); when they differ, or the last review had none, `verification-changed.md` is appended after `incremental.md` and the reviewer rereads the record in full; otherwise it checks only that the new lines are still covered. An edit to the description alone starts no review: the caller's triggers don't include `edited`, and the next push picks the new record up. A push that only merges main carries a passing verdict forward only while the record's hash is unchanged; a changed record makes it a real review. The hash is the only thing about the record that leaves the review job: the workflow's `record` output carries it for the self-test, and the record's text is in no output.

## Testing it

`tests/test_agent_review.py` covers the decisions and the script with a stand-in for `claude`, and the verification record (`Verification`: the file and the section with a record, neither without one or with the input off, the note on a block that doesn't parse, the record's text never in the prompt or the outputs, the hash in the state line and the reread on a changed record); `tests/test_review_outcomes.py` the finding ids, the outcomes merge and its caps, the dismissals and the self-test script `.github/scripts/finding-outcomes-self-test.sh` (which `self-test.yml` runs with the stub reviewer: a blocking finding, a push the stub passes, a dismissal); `tests/test_agent_review_risky.py` the second review's (`risky` with `**` globs and renamed paths, `wanted` on label events and the owner, its own comment lines, the prompts); `tests/test_second_review_order.py` runs the `second-pending` and `second-report` steps as the workflow has them against a fake GitHub that keeps state (`tests/fakes/github`): push then label and label then push, in both finishing orders, an earlier blocking review against a later pass, the owner's "Not a risky" after removing the label, a run writing between another's check and its post, a cancelled label run's pending, re-runs, a push to a new head, forged statuses and comments (a huge or unknown run id, another host or repository, another workflow, event, pull request or head, a lookup that fails), and the single-run cases that behave as before (the self-test runs it too, as `second-review-order`); `tests/test_agent_review_workflow.py` checks the workflow's structure (the checkouts keep no credentials, the secrets appear only in each job's Review step, which runs nothing from the pull request's checkout, the models are literal `sonnet` and `claude-opus-5-5` in their own jobs, each report job has no secret, checks out only fleet's tools (nothing of the pull request) and posts only its own status, the caller and the self-test). The self-test runs the reusable workflow on fleet's own pull requests with `dry-run: true` and `fake-review` set to `pass`, `blocking`, `malformed` and, with `verification: true`, `verification` (a blocking finding of the kind "Verification that doesn't cover the change", read beside this pull request's own record): the stub reviewer `tests/fakes/claude` prints that answer in place of Claude Code (nothing installed, no secret), and a last job checks each reached its verdict (`pass`, `blocking`, `error`, `blocking`) through the workflow's `verdict` output, and warns when the `record` output is empty (the pull request's description carried no record block). Six more calls fake the second review's events (`fake-event`, honoured only with `fake-review`): risky by label, by path, by a `.github/` change, not risky, `unlabeled` by a non-owner (skip: the status stays) and by the owner (re-evaluated), checked through `second-verdict`. fleet's own caller, `.github/workflows/agent-review-caller.yml`, runs the real reviews on its pull requests with `pull_request_target`.
