fleet's own `.github/workflows/release.yml` tags nothing while a changelog fragment is still pending at the release commit: a new step, `Check that no fragment is pending`, runs before `Tag the commit` and fails naming each fragment left in `changelog.d/`. `fleet release prepare` folds every fragment in the release pull request, so one still there at the release commit merged to `main` after prepare ran; `fleet release check` refuses that only on a fleet CI run of the release pull request after the late merge, and GitHub doesn't start one when the base moves. 4.1.0 was tagged that way: its release pull request was cut, and passed fleet CI, before #133 and #134 merged, so its tag carries both changes and its notes neither, #134's breaking one among them under a minor version. A version refused this way stays untagged, and the next release pull request, cut from `main`, folds what's pending (`docs/release.md`, Cutting a release, which also says to bring a release pull request up to date with `main` before merging it if anything merged since `prepare` ran). Tests: `tests/test_release.py` (`ReleaseScriptsTest`: the step fails on pending fragments and names them, passes a release commit with every fragment folded, runs before the tag and the release, and on a copy of the repository passes the tree `prepare` leaves and fails on a fragment added after it, which `fleet self-check` passes). What apps do: nothing; only fleet's own release workflow changes.
