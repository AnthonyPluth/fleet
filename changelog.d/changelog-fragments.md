fleet's changelog is one fragment per pull request (#112, step C): a pull request adds `changelog.d/<name>.md`, front matter `kind: breaking`, `added`, `changed` or `fixed`, then its entry on one line, so pull requests that run at once never conflict on a shared Unreleased section. `CHANGELOG.md` is frozen at 4.0.0, the history above stays, and its Unreleased entries are now fragments with their text unchanged. `fleet release prepare X.Y.Z` folds the fragments into the release's notes, `changelog.d/released/X.Y.Z.md`, one `## [X.Y.Z] - YYYY-MM-DD` section in the CHANGELOG's format (Added, Changed, Fixed; a `breaking` fragment under Changed as `**Breaking:**`), deletes them, and refuses a minor or patch release when a fragment is `breaking`. `fleet release notes X.Y.Z` reads those notes, so `release.yml` is unchanged. `fleet sync-plan` reads the release notes beside the `--changelog` it is given (`changelog.d/released/` in the clone of fleet at the pins' version), and the sync pull request's and the migration issue's bodies list CHANGELOG.md's sections and the later releases' notes together, newest first, so a sync from 4.0.0 or earlier to a later release lists both; `sync.yml` is unchanged. A new `fleet release check --base REF`, run by fleet CI on each pull request except Dependabot's, fails one that adds no fragment (a release pull request, which changes `VERSION`, adds none), a fragment that doesn't parse, an entry added to `CHANGELOG.md` or a change to a release's notes; `fleet self-check` also checks every fragment and that `CHANGELOG.md` gains no `## [Unreleased]` or newer section. What apps do: nothing; their sync pull requests and migration issues read the same sections as before.
