Every merge to `main` is a release of fleet, and nothing in fleet's tree names its version any more (#142, the second part of #112's step D). The new `.github/workflows/release.yml` runs on every push to `main` in three jobs: `make check` on the merged commit (read-only), since two pull requests that each passed can break `main` together; Plan (read-only, a fresh checkout and the runner's own `python3`), which works out the version with `fleet next-version --first-parent --fragments` (each merged pull request's title: `feat:` a minor, `feat!:` or a `BREAKING CHANGE:` line a major, anything else a patch, a docs-only merge too; a `kind: breaking` fragment added since the last tag a major whatever the title says) and the notes with `fleet release notes X.Y.Z --since <the previous tag> --at <the commit>` (the fragments the commit's tree adds to the previous tag's, then each merge that added none by its subject); and Tag and release (`contents: write` only, no checkout, nothing of the repository run), which tags the merged commit through the API and publishes the GitHub Release with `--verify-tag`. One `fleet-release` concurrency group waits instead of cancelling; a commit that isn't `main`'s newest any more is skipped, and the newest's release carries it; a re-run reuses a tag already on its commit, refuses one on another commit and doesn't publish a release twice. Gone: `VERSION`, every reusable workflow's top-level `env: FLEET_REF` (which nothing read since step A), `fleet release prepare`, the release pull request and the stamp checks. `fleet self-check` now fails when one comes back: a `VERSION` file, a `FLEET_REF` key in any workflow, a version other than the constant `0.0.0` in `plugin.json` or `pyproject.toml`, a version other than the placeholder `vX.Y.Z` in a snippet in `docs/`, a version in fleet's own `AGENTS.md` markers (which carry none now, written by `fleet sync --self`, and must equal `agents-md/sections/` byte for byte), and release notes in `changelog.d/released/` after 5.0.0, where it stays frozen. Fragments are never folded again, so `fleet release check` (Release check) also refuses a pull request that changes or deletes a merged fragment or touches `changelog.d/released/`; a revert keeps the reverted pull request's fragment and adds its own. The fixture consumers stay at v5.0.0, the last stamped release, for good. Everything under `fleet_tools/` joins the second review's always-risky paths in fleet's own caller (which listed `release.py` and `next_version.py`), because `release.yml` runs `fleet_tools/cli.py`, which imports every module. What apps do: nothing. Their pins, `.fleet/version`, markers, vendored files and notes, `fleet sync`, `fleet drift`, `fleet --version` and `tools/fleet` are unchanged, and none of their workflows read `VERSION` or `FLEET_REF`; their sync bodies list the fragments of the releases after 5.0.0 first, then the 5.0.0 and 4.1.0 notes and `CHANGELOG.md`'s sections. This merge is fleet's first release of the kind, v6.0.0, a major for #139's breaking fragment, with #138's, #139's, #141's and this entry in its notes. Tests: `tests/test_release.py` (fleet stamp-free; each stamp coming back fails `fleet self-check`; the workflow's triggers, jobs, permissions and concurrency, the write job running only `gh`; the rehearsal on a real repository with a stub `gh`: this merge planned as v6.0.0 with the four pending fragments, tagged and published once, a re-run, merge commits and squash commits alike, later merges releasing only what they add, a Dependabot bump by its subject, rapid merges, a breaking fragment under a `fix:` title, a bad release reverted as the next patch), `tests/test_changelog.py` (a merged fragment changed, deleted or taken by name, `released/` frozen), `tests/test_sync_workflow.py` (sync bodies across the last fold, from v3.1.0, v4.1.0 and v5.0.0 to v6.0.0 and from v6.0.0 to v6.0.1), `tests/test_sync_agents.py` (fleet's own markers without a version) and `tests/test_agent_review_workflow.py` (every `fleet_tools/` module always risky in fleet's own caller).
