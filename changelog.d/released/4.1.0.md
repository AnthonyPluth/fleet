## [4.1.0] - 2026-11-16

### Added

- `fleet drift --own-commit <sha>` and a self-test-only input to `.github/workflows/checks.yml`, `fixture-commit` (string, default empty, which keeps the drift step as it was): the commit to take for the running fleet's own, for fleet's fixture consumers, whose content is fleet's tree under a made-up commit. The self-test's three checks calls and the release rehearsal pass it.
- `fleet sync --self` (#112): fleet's own `AGENTS.md` blocks and its fixture consumers (`tests/fixtures/consumer-*`) re-synced from its tree, each at the version its markers and `.fleet/version` already carry (`fleet release prepare` still moves those), all or nothing. It replaces `fleet sync --to v$(cat VERSION)` in fleet's own checkout, which `sync --to` now refuses on any commit but the release's.
- The security scans' image scan can take a list of accepted findings: a new input to `.github/workflows/security.yml`, `trivy-image-ignore-file` (string, default empty, which leaves the image scan as it was), names a Trivy YAML ignore file in the caller's repository (`.trivyignore.yaml`). The `Trivy (image)` job reads it from the tip of the repository's default branch through the API, on every event, never from its checkout, which on a pull request is the pull request's own merge commit: an entry counts only once the owner has merged it, so no pull request, from a fork or not, accepts its own findings. `.github/scripts/trivy_ignore.py` (standard library, `python3 -I`) checks the file and writes Trivy a copy of what it understood, outside the workspace: only `vulnerabilities:`, and each entry needs an `id`, exact `paths` (no wildcards, so the same CVE elsewhere in the image is still reported; a `purls` item, which may narrow an entry further, is a plain `pkg:<type>/<name>` that Trivy's parser accepts), a `statement` and an `expired_at` at most 180 days away; an expired entry is dropped with a warning and its finding is reported again; a file that can't be read or checked fails the job; a file that isn't on the default branch accepts nothing. With the input set the job also deletes the checkout's `trivy.yaml` and `.trivyignore` before the image scan, which Trivy would otherwise read from the pull request. The `Trivy (files)` job checks the checkout's own copy by the same rules without using it, so a pull request that adds an entry the image job would refuse, a list over 64 KiB or a symbolic link in its place fails itself (fleet's Self-test names a fixture list, so that check runs in fleet's CI); the file scan never accepts anything from the list, and without the input both scans are unchanged. What apps do: nothing to keep working; to accept a finding, pass `trivy-image-ignore-file: .trivyignore.yaml`, and merge the entry before the change that needs it. `docs/adopting.md` (Accepted image findings); `tests/test_security_trivy_ignore.py` and the Self-test's `accepted-finding` job, which hands the list the script writes to the pinned Trivy through the pinned `trivy-action`'s `trivyignores`, as the image job does.

### Changed

- fleet's changelog is one fragment per pull request (#112, step C): a pull request adds `changelog.d/<name>.md`, front matter `kind: breaking`, `added`, `changed` or `fixed`, then its entry on one line, so pull requests that run at once never conflict on a shared Unreleased section. `CHANGELOG.md` is frozen at 4.0.0, the history above stays, and its Unreleased entries are now fragments with their text unchanged. `fleet release prepare X.Y.Z` folds the fragments into the release's notes, `changelog.d/released/X.Y.Z.md`, one `## [X.Y.Z] - YYYY-MM-DD` section in the CHANGELOG's format (Added, Changed, Fixed; a `breaking` fragment under Changed as `**Breaking:**`), deletes them, and refuses a minor or patch release when a fragment is `breaking`. `fleet release notes X.Y.Z` reads those notes, so `release.yml` is unchanged. `fleet sync-plan` reads the release notes beside the `--changelog` it is given (`changelog.d/released/` in the clone of fleet at the pins' version), and the sync pull request's and the migration issue's bodies list CHANGELOG.md's sections and the later releases' notes together, newest first, so a sync from 4.0.0 or earlier to a later release lists both; `sync.yml`'s only change adds `changelog.d` to its checkout of fleet, so the self-test's copy of fleet at the pin carries the notes as the real clone does. A new `fleet release check --base REF`, run by fleet CI on each pull request except Dependabot's, fails one that adds no fragment (a release pull request, which changes `VERSION`, adds none, and fails if a fragment merged to `main` after `prepare` ran is still pending in the tree it merges into), a fragment that doesn't parse, an entry added to `CHANGELOG.md` or a change to a release's notes; `fleet self-check` also checks every fragment and that `CHANGELOG.md` gains no `## [Unreleased]` or newer section. What apps do: nothing; their sync pull requests and migration issues read the same sections as before.
- fleet's tools identify themselves by commit, not by `VERSION` (#112, step B): a new `fleet_tools/identity.py` takes the running fleet's commit from `git rev-parse HEAD` in a checkout, or from `vcs_info.commit_id` in `direct_url.json` (PEP 610) for an install from git such as `tools/fleet`'s `uvx --from "git+https://github.com/AnthonyPluth/fleet@<commit>"`. `fleet --version` prints that commit, and the tag when `git describe --exact-match` finds one (it printed `VERSION`, which mislabelled every commit between releases). `fleet sync --to vX.Y.Z` refuses unless the commit that version names (the workflow pins at it, `--commit`, or the tag's from `git ls-remote`) is the running one, rather than comparing `--to` with `VERSION`; `vX.Y.Z` is still the label it writes into the markers, the vendored notes, the marketplace `ref` and `.fleet/version`. `fleet drift`'s "this block is at fleet's own version" now means `.fleet/version`'s commit is the running commit (read from this fleet's files), anything else being read from the version's tag in fleet's history; its other rules don't change. The consumer side doesn't change: the apps' pins, `.fleet/version`, the markers, the vendored notes and `tools/fleet` stay as they are, and no caller has to change anything. `checks.yml`, `docker.yml`, `mining-tasks.yml`, `review-mining.yml` and `sync.yml` no longer check out `VERSION`, and `sync.yml`'s self-test path no longer stamps a copy's `VERSION`: its fixture builder pins the running commit. `VERSION`, `FLEET_REF`, `fleet release prepare` and `release.yml` are unchanged, and `VERSION` is read only by them and `fleet self-check`'s stamp checks until fleet releases on every merge (#112, step D).
