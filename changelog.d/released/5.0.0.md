## [5.0.0] - 2026-11-16

### Changed

- **Breaking:** 4.1.0 already shipped this change without this entry: its release pull request was cut before #134 merged and was merged after it, so v4.1.0's tag carries the change and its notes leave it out, a breaking change under a minor version. Treat 4.1.0 as part of this 5.0.0 migration: an app whose pins move to 4.1.0 gets this change there, before 5.0.0. The security scans no longer read Trivy's settings files from the caller's checkout (#132, owner decision), so a pull request can't silence either Trivy scan by adding one. Trivy v0.70.0 reads three files from its working directory when they exist (confirmed in its source and with the pinned binary): `./.trivyignore` (`--ignorefile`, ids to drop for every scanner), `./trivy.yaml` (`--config`: any option, among them `skip-files`, `skip-dirs` and another `ignorefile`) and `./trivy-secret.yaml` (`--secret-config`: secret rules to disable, paths to allow, found while checking the first two and closed with them since it silences the secret scan the same way). In `.github/workflows/security.yml`'s `Trivy (files)` and `Trivy (image)` jobs that directory is the checkout, which on a pull request is the pull request's own merge commit. Both jobs now run `.github/scripts/security-trivy-settings.sh` before the scan, on every event and whatever the inputs: it writes empty ones outside the workspace, which the scan step names in `TRIVY_CONFIG`, `TRIVY_IGNOREFILE` and `TRIVY_SECRET_CONFIG`, so Trivy doesn't look for them in the checkout at all, and it warns on the run naming each of the three it found. The file scan leaves the checkout's three in place and scans them like any other file, so a secret committed in one (a registry password in `trivy.yaml`, say) is still reported (the empty secret settings are a file named `.git`, since Trivy's secret scan skips the root file that has its secret settings' name, which would otherwise be the checkout's `trivy-secret.yaml`, and no file a repository tracks can be named `.git`); the image job, whose scan reads the built image and not the checkout, also removes them after the build, as a second barrier. Both scans also pass `trivy-action` a `cache-dir` under the runner's temporary directory in place of its default in the workspace (`.cache/trivy`), so a checkout can't bring its own vulnerability database; the first run afterwards downloads the database again. No `TRIVY_*` variable reaches the scans from a caller (a caller's `env` isn't passed to a called workflow), and `trivy-action` sets the scan's options from `security.yml`'s own inputs, which already overrode a `trivy.yaml`. The image job did the removal only with `trivy-image-ignore-file` set (#129); the file scan never did. Why a major: no input, permission, secret, status or output changes, but a default changes what an existing setup does, since a repository with one of the three files gets its dropped findings reported again, and with `sarif-upload: false` or `fail-on-findings: true` its Trivy jobs then fail. The accepted findings are the image's only, through `trivy-image-ignore-file`'s list on the default branch; there is no opt-out input and no list for the file scan, and `trivy.yaml` is not read from the default branch either (its legitimate uses the scans lack are a skip list, a timeout and a database mirror; a skip list hides whatever is under it and carries no statement or expiry, so one would be a fleet input, on request). It applies on a push to `main` and the weekly run too, so a scan of `main` reads what a pull request's scan reads. Comments Trivy honours in the scanned files (`#trivy:ignore:<id>`) are unchanged. What apps do: Darkroom, Waypoint and Runway have none of the three files, so nothing but the manual `fleet sync` a major asks for; a repository that has one deletes it, moves an image finding it still accepts into the list `trivy-image-ignore-file` names, and fixes the rest or dismisses its alert in the Security tab (`docs/adopting.md`, "Trivy's settings files in the checkout"). Tests: `tests/test_security_trivy_settings.py` (the script on files, links and directories of those names, kept and removed; both jobs run it with no condition, before the scan and after the build; the scan steps' environment and cache directory) the Self-test's new `checkout-trivy-settings` case, where the pinned Trivy, through the pinned `trivy-action`, reports none of three planted findings while the three files are read and all three with the file scan's step and environment, and reports a made-up secret planted inside each of the checkout's own three files when it scans the workspace; and the Self-test's `accepted-finding` case, which now runs with the image scan's environment, so the list in `trivyignores` is shown to replace the empty ignore file.

### Fixed

- fleet's own `.github/workflows/release.yml` tags nothing while a changelog fragment is still pending at the release commit: a new step, `Check that no fragment is pending`, runs before `Tag the commit` and fails naming each fragment left in `changelog.d/`. `fleet release prepare` folds every fragment in the release pull request, so one still there at the release commit merged to `main` after prepare ran; `fleet release check` refuses that only on a fleet CI run of the release pull request after the late merge, and GitHub doesn't start one when the base moves. 4.1.0 was tagged that way: its release pull request was cut, and passed fleet CI, before #133 and #134 merged, so its tag carries both changes and its notes neither, #134's breaking one among them under a minor version. A version refused this way stays untagged, and the next release pull request, cut from `main`, folds what's pending (`docs/release.md`, Cutting a release, which also says to bring a release pull request up to date with `main` before merging it if anything merged since `prepare` ran). Tests: `tests/test_release.py` (`ReleaseScriptsTest`: the step fails on pending fragments and names them, passes a release commit with every fragment folded, runs before the tag and the release, and on a copy of the repository passes the tree `prepare` leaves and fails on a fragment added after it, which `fleet self-check` passes). What apps do: nothing; only fleet's own release workflow changes.
- 4.1.0 already shipped this fix without this entry (its release pull request was cut before #133 merged). The accepted image findings' check (`trivy-image-ignore-file`, `.github/scripts/trivy_ignore.py`) holds a purl to the rules Trivy v0.70.0's purl parser (`packageurl-go` v0.1.5) has for five types, and says which rule a refused purl broke instead of describing a form the purl already had: `cpan`, `swift` and `vscode-extension` need a namespace (`cpan`'s in capitals), `otp` takes none, and `julia` needs a `uuid` qualifier, so no `julia` purl is accepted. Those five types were refused outright before; the forms the parser takes (`pkg:cpan/AUTHOR/Name`, `pkg:otp/name`, `pkg:swift/github.com/owner/name`, `pkg:vscode-extension/publisher/name`) are now accepted. `cran` and `conan` purls stay accepted as they were: that parser has no rule for either (earlier `packageurl-go` releases did). The Self-test's `accepted-finding` job again hands the real Trivy a path-only entry as well as one with `purls`, and the latter now carries every form the check accepts of every type the parser knows (`tests/fixtures/security/purls.txt`: with and without a namespace, with and without a version, so the versionless `pkg:swift/github.com/owner/name` form too; a test holds the fixture to exactly those forms), so a Trivy that refuses one fails fleet's Self-test, not an app's image scan. The job has a control as well: a list holding one purl the parser refuses (`pkg:swift/name`), on an entry that matches no finding, must fail its scan and for that purl, so a pass shows Trivy parsed the fixture's purls rather than skipped them. A test fails when `TRIVY_VERSION` moves without the rules being read again from the new Trivy's parser (`PURL_RULES_FROM`; `docs/adopting.md` says how). What apps do: nothing.
