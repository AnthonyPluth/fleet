`fleet next-version --first-parent --fragments`, `fleet release notes X.Y.Z --since vW [--at REF]` and changelog fragments in the sync bodies (#141, the first part of #112's step D, releasing fleet on every merge): with `--first-parent` the planner reads only the first-parent commits since the last tag (each merged pull request's title, never the commits on its branch), and with `--fragments` a `kind: breaking` fragment added since that tag's tree makes the release a major whatever the titles say; `--since` prints the notes of a release made from `--at` (default `HEAD`): the fragments its tree adds to `vW`'s (`git diff --diff-filter=A`, `changelog.d/released/` left out), grouped as a release's notes are, then under Changed the subject of each first-parent commit that added none (a Dependabot bump). Nothing runs those two yet: fleet still releases through a release pull request, and the switch is step D's second part. `sync.yml` now fetches the content's tag beside the pins' (both one commit deep, no token), and `fleet sync-plan` lists in the sync pull request's or migration issue's body, under "Releases after vA, up to vB" and before the folded notes, the fragments the pins' tree adds to the content's, so a sync to a release without a `changelog.d/released/X.Y.Z.md` still gets its entries; when the tag can't be fetched the body says the fragments couldn't be read, links fleet's releases, and the sync goes on. For fleet's own pull requests the changelog check moves from fleet CI's `make check` job to a new workflow, "Release check" (`.github/workflows/release-check.yml`, which also runs on `edited`), running `fleet release check` on the runner's own `python3` with the pull request's title and description (`--title`, `--body`, from the event through `env`): a `kind: breaking` fragment needs a title that says so (`feat!:`, or a `BREAKING CHANGE:` line in the description), a title or description that says so needs a `kind: breaking` fragment, and a `#major` or `#minor` at the end of the title is refused, since the ` (#N)` GitHub adds after it in the merge commit's subject keeps it from reaching `main`. `release-check.yml`, `fleet_tools/release.py` and `fleet_tools/next_version.py` join the second review's always-risky paths in fleet's own caller. What apps do: nothing. An app's `docker.yml` passes neither new flag, so its versions come out as before; its sync bodies to any release up to 5.0.0 are unchanged but for 4.1.0, the one tag whose tree holds pending fragments, whose two the body now lists. Tests: `tests/test_next_version.py` (first-parent titles only; a breaking fragment forcing a major under a `fix:` title; only fragments added since the last tag; skip, reuse and the highest tag; a fragment that doesn't parse; the apps' default reading none), `tests/test_changelog.py` (`NotesBetweenTreesTest`, the title and fragment rules, `ReleaseCheckWorkflowTest`), `tests/test_sync_workflow.py` (the fragments block and its fallback, the command against a tagged clone, the step fetching the content's tag) and `tests/test_agent_review_workflow.py` (the release check and the release tools stay always risky).
