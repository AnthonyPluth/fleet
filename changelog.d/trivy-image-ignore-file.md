The security scans' image scan can take a list of accepted findings: a new input to `.github/workflows/security.yml`, `trivy-image-ignore-file` (string, default empty, which leaves the image scan as it was), names a Trivy YAML ignore file in the caller's repository (`.trivyignore.yaml`). The `Trivy (image)` job reads it from the tip of the repository's default branch through the API, on every event, never from its checkout, which on a pull request is the pull request's own merge commit: an entry counts only once the owner has merged it, so no pull request, from a fork or not, accepts its own findings. `.github/scripts/trivy_ignore.py` (standard library, `python3 -I`) checks the file and writes Trivy a copy of what it understood, outside the workspace: only `vulnerabilities:`, and each entry needs an `id`, exact `paths` (no wildcards, so the same CVE elsewhere in the image is still reported), a `statement` and an `expired_at` at most 180 days away; an expired entry is dropped with a warning and its finding is reported again; a file that can't be read or checked fails the job; a file that isn't on the default branch accepts nothing. With the input set the job also deletes the checkout's `trivy.yaml` and `.trivyignore` before the image scan, which Trivy would otherwise read from the pull request. The `Trivy (files)` job checks the checkout's own copy by the same rules without using it, so a pull request that adds an entry the image job would refuse fails itself; the file scan never accepts anything from the list, and without the input both scans are unchanged. What apps do: nothing to keep working; to accept a finding, pass `trivy-image-ignore-file: .trivyignore.yaml`, and merge the entry before the change that needs it. `docs/adopting.md` (Accepted image findings); `tests/test_security_trivy_ignore.py` and the Self-test's `accepted-finding` job, which hands the list the script writes to the pinned Trivy through the pinned `trivy-action`'s `trivyignores`, as the image job does.
