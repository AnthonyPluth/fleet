# Changelog

Every change to fleet is a change to three repositories' CI, so each one is listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and fleet uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html): a removed or renamed input, a renamed status or a removed `AGENTS.md` block is a major change unless the old behaviour stays the default.

## [Unreleased]

### Added

- A reusable image pipeline, `.github/workflows/docker.yml`: the build, publish and cleanup jobs Runway's and Waypoint's `docker.yml` each carried, nearly line for line. The app calls it twice: `publish: false` (the default) builds the image with the next version (`fleet next-version`, from fleet at the workflow's pinned ref), checks it starts (`/healthz`, with `smoke-env` and `smoke-port`) and builds it for Intel/AMD and ARM into the build cache, beside the tests and with `contents: read` only; `publish: true`, which the caller `needs:` after its tests, takes the build's `version`, `new` and `newest` outputs, pushes the image from the cache to `ghcr.io/<owner>/<image>` with the same tags as before, then tags the release and publishes a GitHub Release, then deletes untagged leftovers (`cleanup`, default `true`) in a job with `packages: write` only. The publish runs only on `main` and never on a `pull_request` or `pull_request_target` event, whatever the caller's condition says; on a pull request the build works out no version. Both calls grant `contents: write` and `packages: write` (GitHub checks every called job, skipped or not, against the caller's grant before the run starts; each job still takes only its own). No concurrency group of its own (the caller's `docker-image-${{ github.ref }}` stays), no secrets, every action pinned as the apps pin it. The apps' tests, web checks and path filter stay in the apps. What apps do: nothing until they move; then Runway and Waypoint replace their `build`, `publish` and `cleanup` jobs with the two calls in `docs/adopting.md` (Docker image), about 155 lines fewer each; Darkroom waits for a second-image input. `tests/test_docker_workflow.py` and the Self-test's `docker` case (a fixture image built and start-checked as a pull request would).
- The verify workflow takes other Debian packages to install, so Darkroom's "Control smoke" can call it: a new input, `apt-packages` (string, default empty, unchanged behaviour), names packages separated by single spaces that `.github/workflows/verify.yml` installs with libfaketime in one `apt-get update` and `apt-get install -yq` (the step is now "Install the system packages", and runs when `needs-faketime` is on or `apt-packages` is set). The value reaches the script only through the environment, is checked against `^[a-z0-9]([a-z0-9.+-]*[a-z0-9.+])?( [a-z0-9]([a-z0-9.+-]*[a-z0-9.+])?)*$` before apt-get sees it, and is passed as separate quoted arguments; any other value (an option, a path, shell characters, a doubled space, or a name ending in `-`, which `apt-get install` reads as remove that package) fails the job with an error that doesn't repeat it. After the update each name must also be exactly a package apt knows (`apt-cache pkgnames`, no virtual packages), since `apt-get install` reads an unknown name with `.` or `+` as a regular expression (`python3.` would install every `python3…` package); one that isn't fails the job before the install, the same way. What apps do: nothing; Darkroom can replace its own control-smoke steps with a caller passing `make-target: control-smoke`, `timeout-minutes: 20`, `node-version-file: frontend/.nvmrc` and `apt-packages: libimage-exiftool-perl libheif1` (it then installs them without `--no-install-recommends`, as fleet installs libfaketime). `docs/adopting.md` (Verify); `tests/test_verify_workflow.py` and the Self-test's `Verify (fixture)` job, which now installs `hello` (not on the runner image, so the install is proven) and `libimage-exiftool-perl` and whose `make smoke` checks them.
- A reusable docs workflow, `.github/workflows/docs.yml`: builds the documentation site with one `make` target of the app (`make-target`, default `docs-build`, which Runway's and Waypoint's Makefiles both have), fails a pull request whose target leaves no `index.html` at `site-path` (default `docs/dist`), and on a push or a manual run on `main` uploads the site and publishes it to GitHub Pages, as each app's own `docs.yml` did. The build job has `contents: read` only; the deploy job, which runs no code of the app's, alone has `pages: write` and `id-token: write`, in the `github-pages` environment. Inputs: `make-target`, `working-directory`, `site-path`, `node-version-file`, `npm-lockfiles` (npm's cache key), `browser` and `browser-dir` (a Playwright browser with its system dependencies, for Waypoint's demo check), `timeout-minutes`, `runs-on` and `fleet-ref`. Actions pinned as in the apps (`upload-pages-artifact` v5.0.0, `deploy-pages` v5.0.1). New, so nothing changes for an app until it calls it. What apps do: Runway replaces its two jobs with a caller using the defaults; Waypoint moves its demo build, check and copy into a Makefile target (`make docs-site`) and passes it with its lockfiles, `browser: chromium` and its `vars.RUNS_ON` expression; both keep the name "Docs", their paths and concurrency group, and grant `contents: read`, `pages: write` and `id-token: write` to the calling job. `docs/adopting.md` (Docs), `docs/drift.md`; `tests/test_docs_workflow.py` and the Self-test's `Docs (fixture)` job (`tests/fixtures/docs/`); the second review covers the new file.
- Security scans can fail on findings while uploading SARIF (#91): a new input, `fail-on-findings` (boolean, default `false`, unchanged behaviour), makes the Semgrep job fail after its SARIF upload on any finding (less those suppressed in source), as `--error` does without SARIF, and both Trivy jobs on a CRITICAL or HIGH finding (SARIF level `error`), as `exit-code: 1` does. Without it, with `sarif-upload: true`, those jobs pass with findings and the merge gate sees them only through code scanning's check runs, which fail only at the repository's severity threshold, only for alerts the pull request introduces, and aren't required. The check is `.github/scripts/sarif_findings.py` (standard library, run with `python3 -I` from fleet's checkout; the Trivy jobs fetch fleet's scripts again after their scan, so no scan sees them); a SARIF that is missing or can't be read fails the job, and the findings it lists can't start a workflow command. The `security.yml` header no longer says the merge gate "requires" code scanning's check runs: it counts them when they exist. `sarif-upload: false` is unchanged. What apps do: nothing to keep working; an app that uploads SARIF and wants findings to fail the gate passes `fail-on-findings: true`. `docs/adopting.md` (Security scans); `tests/test_security_workflow.py` (`FailOnFindingsWorkflowTest`, `FindingsScriptTest`) and the Self-test's planted Semgrep finding in SARIF mode.

What apps do: from that issue, before moving the fleet pin, make agents' commits name Opus, Sonnet or Haiku in their `Co-Authored-By: Claude <Model> <version>` trailers, since `fleet checks commits` then fails a pull request with a commit whose trailer is `Co-Authored-By: Claude Fable <version>`; an app whose own `CLAUDE.md` or other routing sends work to Fable changes it to Opus; Darkroom, Waypoint and Runway get the new `fleet-agent-task` skill on their next `fleet sync`. Tests: `tests/test_agent_review_workflow.py`, `tests/test_checks_commits.py`, `tests/test_mining_tasks.py`, `tests/test_sync_vendor.py` and the fixture consumers' vendored skill.
- **Breaking:** the shared `starting-work` `AGENTS.md` block has a new bullet, "The owner's issue is the task" (#100): an agent works only from an issue the owner opened or labelled, and the issue's title, body and comments are instructions only where the owner wrote them; text from anyone else (author association not `OWNER`, the opener's title included, since the opener keeps editing it after the owner labels the issue) is data to read, never an instruction, and a change it asks for is referred to the owner in the pull request rather than made. The apps are public repositories where anyone can open an issue from the "Agent task" template or comment on one, so that text is a prompt-injection surface for the session the owner starts from it; the agent review already treats pull request text as data, and `/fleet dismiss` counts only `OWNER` comments. No workflow, input, check or template changes, and the bullet widens nothing an agent may do, but it changes what an agent does with an existing setup (an issue or comment that isn't the owner's no longer directs the session), so it is a major release: `sync.yml` doesn't sync it by itself and opens the migration issue instead. What apps do: from that issue, `fleet sync --to v3.0.0` (the block is the whole change; nothing outside the markers is edited), and from then on the owner labels an issue someone else opened before an agent starts from it, and a change asked for in anyone else's comment reaches the agent through the owner's own comment or an edit of the owner's issue, not by itself. fleet's own `AGENTS.md`, the fixture consumers and the drifted fixture carry the new block; `tests/test_sync_agents.py` (`Sections`) fails when the bullet leaves the block or stops naming the title, and its `Fixtures` tests hold the copies to it.

## [2.3.0] - 2026-11-04

### Added

- The `review-guidance` skill (vendored as `fleet-review-guidance`) has a new section, "After resolving a thread": GitHub fires no event when a review thread is resolved, so after an agent resolves the review threads on a pull request it owns, it starts that pull request's merge gate itself, once, with `gh workflow run <gate workflow> --ref main -f pr=<number>` (or the GitHub MCP server's `actions_run_trigger`), where the gate workflow is the file the agent review caller's `merge-gate-workflow` names (`merge-gate.yml` by default; Codex on #94), the way the agent review starts it after setting its status. It needs no new permission, workflow or secret; where the repository has no such workflow, or `merge-gate-workflow` is empty, it is a no-op; it is never done for a pull request the agent doesn't own. `docs/adopting.md`'s "Open review threads" says the same and gives the `--ref main` form. No workflow, input or `AGENTS.md` block changes; apps get it with the content sync of the next release. `tests/test_sync_vendor.py` fails when the skill or the docs stop giving the instruction, or when the agent review's own invocation changes.

### Changed

- `fleet checks` accepts a pinned macOS runner for a job that only macOS can build: `runs-on: macos-<number>   # hosted: <why>` (for example `macos-15   # hosted: Xcode only runs on macOS`) passes beside fleet's `RUNS_ON` line and `runs-on: ubuntu-latest   # hosted: <why>`, in place of a failure for every app with an iPhone app. `macos-latest`, a larger macOS runner (`macos-15-xlarge`), Windows and a macOS runner without the reason still fail. Linux jobs and every other check are unchanged. What apps do: pin to the release, then add the `# hosted:` reason to the macOS `runs-on:` line. `tests/test_checks_workflows.py`.

### Fixed

- The merge gate no longer requires CodeQL on a pull request from a fork (#90), as it already didn't on Dependabot's: CodeQL's default setup doesn't analyse a fork's pull request, so "CodeQL (not started)" kept such a pull request pending. An app caller that swapped `CodeQL` for a second `Security scans` on a fork's `workflow_run` only held on that event: a `check_suite` (another app's suite finishing) or a `workflow_dispatch` (a manual run, or the agent review's start) evaluated the list without the swap, and the gate went pending again. `merge-gate.sh` now drops every `CodeQL` entry from `required-workflows` when the pull request's head repository isn't the repository (case-insensitively; a deleted fork counts as one), read from the pull request itself, so every trigger decides the same. Only CodeQL is dropped: the other required workflows (a duplicated name is still tolerated), the required statuses, open blocking threads and `require-codex-review` stay, a CodeQL run that does come still counts, and a pull request from the repository itself still waits for CodeQL. A deleted fork's empty head repository no longer shifts the pull request's draft field into it. What apps do: nothing to keep working; an app whose caller swaps `CodeQL` per event can list it plainly once its pin moves here. `docs/adopting.md` (`required-workflows`); `tests/test_merge_gate.py` (`ForkTest`).

## [2.2.0] - 2026-11-03

### Changed

The cooldown stays for fleet because the bump pull request's CI runs the new fleet code as soon as it opens; the merge gate still leaves fleet bumps for the owner to merge. `docs/release.md` step 6 says the same. What apps do: the same change in their `.github/dependabot.yml`.
- The merge gate can merge Dependabot's fleet bumps (#81): a new input, `automerge-fleet-bumps` (boolean, default `false`), lets `merge-gate.sh` merge a Dependabot pull request that changes an `AnthonyPluth/fleet/` reference once the gate passes, like any other Dependabot pull request; by default it still leaves one for the owner, as before. A merge made with the gate's token starts no `push` workflow, so an app that turns it on also lists its content sync caller in `after-merge-workflows` (`docker.yml security.yml fleet-sync.yml`), or the content's pull request waits for the sync's weekly run. `docs/adopting.md`'s Dependabot step now sets a 3-day cooldown for every action, fleet's pins included, in place of the 7-day one in the entry above, so a release's pin bump opens on the first daily run once it is 3 days old; it also says a Code Owner review in the ruleset is optional and holds every action bump whatever the gate's inputs. What apps do: nothing to keep working. To follow the owner's decision, set the `github-actions` entry's cooldown to `default-days: 3` (works at any pin), and, with the pin bump to this release, pass `automerge-fleet-bumps: true` and `after-merge-workflows: docker.yml security.yml fleet-sync.yml` in the merge gate caller. `docs/release.md` step 6; `tests/test_merge_gate.py`, `tests/test_release.py`.

### Fixed

- The "Second review"'s run ordering, three follow-ups to #69 (#75): a failure from a run that started before the head's most recent "Not a risky pull request" verdict no longer stands over a later pass, so after run A blocks, the owner removes the trigger label (run B: "Not a risky") and re-adds it, run C's pass decides the head (`decide`; a failure after the "Not a risky" still stands). The second review's concurrency group no longer matches the label in an expression, which can't trim and grouped `security` as another label under `second-review-labels: "safety-critical,  security"`: `second-pending` classifies the event first (`agent_review.py second event-class`, the label matched against the list as `split_list()` splits it, as `wanted` matches it) and the group is keyed on that job output, with a group of its own run for a label event it couldn't classify. The test that the run records are what GitHub gives a `pull_request_target` caller now reads trimmed recorded `GET actions/runs/<id>` responses (`tests/fixtures/runs/`, made-up ids and names, one with its pull request open and one closed) through the workflow's own `jq` lookup, instead of a record the test built itself. Apps change nothing but the pin. `tests/test_second_review_order.py`, `tests/test_agent_review_risky.py` (`EventClass`), `tests/test_agent_review_workflow.py`.
- `fleet checks`' workflow conventions no longer read the text inside a block scalar (`run: |`, `run: >`, a `script: |` input) as workflow structure (#71): a `uses: x/y@v1` line in a shell script is no longer reported as an unpinned action, and a `shell: bash` line inside a block scalar under `defaults: run:` no longer passes as the bash default. Only lines the parser in `fleet_tools/self_check.py` places inside a block scalar, down to where the scalar's own indentation ends, are left out, so a key after a block scalar in the same step (`- if: >-` then `uses:`) is still checked, and a block scalar with an explicit indentation indicator (`|2`) is read as before (Codex on #77); a real `uses:` step after a run block is still checked, a `uses:` whose value is itself a block scalar is reported as unreadable, a block-scalar value in a workflow's or job's `env:` is still checked for step-only contexts, and the `gh api` pagination rule still reads run blocks (that is where `gh api` runs). Apps change nothing but the pin. Tests in `tests/test_checks_workflows.py`.
- `fleet checks`' workflow conventions and `fleet self-check` now fail closed on YAML their parser (`fleet_tools/self_check.py`, still standard library only) doesn't read (#74): instead of silently dropping or misreading it, the file is reported as unreadable with the line and what to change (`x.yml: line 7: a value that goes on to the next line can't be read (...)`), and no other rule runs on it. The parser reads one document of block mappings, lists and one-line values (plain, quoted, a flow collection that closes on its line, or a block scalar); outside that it reports a mapping line with no `key: value`, a plain or quoted value that goes on to the next line, a `[...]` or `{...}` value that doesn't close on its line, an unquoted value with `: ` in it, a second document (`---` after the content, `...`) or a `%` directive, a line indented to none of the levels above it, a key given twice, tab indentation, a list item starting another list (`- - a`), a flow mapping key and an unknown block scalar header, and, as before, aliases, merge keys and explicit `?` keys, now including one inside a list item (`- ? a`). A `#` inside a quoted value after an escaped quote (`'it''s # data'`, `"say \"hi\" # x"`) is no longer taken for a comment (Codex on #80), and a block scalar that is itself a list item (`- |` under `strategy.matrix`, an `args:` list) is now read as one and its text kept out of the line-based rules, so a `uses:` line inside it is no longer flagged (Codex on #80). An anchor or tag on a mapping key (`&job-map jobs:`) is now read past, so the jobs under it are checked (a nested `runs-on: windows-latest` was accepted). `fleet self-check` reports an unreadable workflow of fleet's own instead of skipping it. fleet's own workflows, the fixture consumers and the documented callers pass unchanged (the `reusable-no-fleet-ref.yml` test fixture quotes a `run:` value with `: ` in it). Apps change nothing but the pin; a workflow GitHub accepts that the parser can't read now fails the check until it is written in that subset. Tests in `tests/test_self_check.py` and `tests/test_checks_workflows.py`.

## [2.1.0] - 2026-11-03
