# Changelog

Every change to fleet is a change to three repositories' CI, so each one is listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and fleet uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html): a removed or renamed input, a renamed status or a removed `AGENTS.md` block is a major change unless the old behaviour stays the default.

## [Unreleased]

## [2.0.0] - 2026-11-03

### Changed

- **Breaking:** the shared `mistakes` and `git-and-prs` `AGENTS.md` blocks and the `review-guidance` skill no longer say the independent "Agent review" runs on, and is required for, every pull request: they name the "Second review" (which passes a pull request that isn't risky), open P1 and P2 review threads, and the "Agent review" where the app turns it on, so an app with the first review off no longer contradicts its own blocks. This closes #58's first part (its second part, `require-codex-review`, is above). The blocks reach an app on its next `fleet sync --to v2.0.0`; an app edits nothing outside them.
- **Breaking:** the owner's review policy is now fleet's default, as #60 asked (the owner's decision), so an app's callers stop carrying it: `agent-review.yml`'s `first-review` defaults to `false` (no independent "Agent review" status or comment; the second review still runs on a security-sensitive pull request, by `second-review-labels`, `second-review-paths` or `second-review-always`, and passes any other with "Not a risky pull request"), and `merge-gate.yml`'s `required-statuses` defaults to `Second review` alone. The gate's default already fails on a blocking "Second review" and on any open Codex P1 or P2 thread; `tests/test_merge_gate.py` (`DefaultPolicyTest`) now pins exactly that. To change: an app that passes `first-review: false` and `required-statuses: Second review` drops both; one that wants the first review keeps or adds `first-review: true` and `required-statuses` listing `Agent review` and `Second review`. fleet's own caller and self-test follow the default (the self-test's first-review cases pass `first-review: true`). The shared `AGENTS.md` blocks and the `review-guidance` skill still describe the "Agent review" as running on every pull request; rewording them (#58's first part) ships separately.

### Added

- `merge-gate.yml` takes `require-codex-review` (default `false`, which changes nothing): `true` keeps the gate pending ("Codex review of this commit") until `chatgpt-codex-connector[bot]` has reviewed the head commit, by a pull request review on it or its own comment whose "Reviewed commit" (7 or more leading hex digits) or `codex-review-state` line names it; an older commit's review doesn't count, a read that fails stays pending, and Dependabot's pull requests are exempt. `docs/adopting.md` adds the `issue_comment` job a `merge-gate-threads` caller needs for it (fleet issue #58's second part). The fake `gh` serves `issues/<n>/…` paths.

## [1.1.0] - 2026-11-03

### Added

- Loop health (`FLEET-LOOP-STATS`): `fleet loop-stats --repo OWNER/NAME --days 30 --json OUT.json --markdown OUT.md [--app-root DIR]` (`fleet_tools/loop_stats.py`) counts, per repository over the window: the pull requests merged in it, how many had an "Agent review" and a "Second review", their findings by severity and how many were resolved, dismissed and open at merge, with shares (from `review_outcomes.load` and the merge-time snapshot `review-mine` uses); where `[tool.fleet.verification]` is set, the records, `verified` and `not verified` dimensions, mean `not verified` per record and the changed paths no guide covers; the report's rows and ticks and the `mined-from` issues opened from them, and those closed in the window; the default branch's commits touching `context.md`, `invariants.md`, the verification guides, the app's own skills (not `fleet-*`) and `.semgrep/`, the "Mistakes that keep coming back" items that became `checked:` between the window's first and last commits, and the days since each guidance file changed; `.fleet/version` and whether a `fleet/sync` pull request is open. The JSON is schema 1 (`docs/loop-stats.md`); a share with a zero denominator is `null` (`n/a` in Markdown), and a part that can't be read (a failing call, a list over its cap, a pull request's changed files at GitHub's 3,000-file cap, which `review-mine`'s verification gaps now treat as unread too, a file that isn't UTF-8, a verification guide that can't be loaded, which nulls the guide counts and uncovered paths, a `pyproject.toml` that can't be parsed, which also nulls the distinct harness commit total) is `null` and named in `missing`, never zero. `review-mining.yml` runs it before rewriting the report (new input `loop-stats-days`, default `30`; new output `loop-stats-url`; no new permission, `contents: read` was already there), appends its Markdown to the job summary and uploads `loop-stats.json` (`actions/upload-artifact`, SHA-pinned, `retention-days: 90`), and `fleet review-mine --stats loop-stats.json` (`fleet_tools/loop_health.py`) puts a "Loop health" section at the top of the report with last run's numbers beside this run's (only when both cover the same number of days), read from the hidden second line `<!-- loop-stats <base64 JSON> -->` it writes, under a strict schema and a 2,048-byte cap (a malformed, misplaced or oversized line is ignored; an unreadable stats file, including one missing a key, holding one loop-stats doesn't write, or written for another repository, keeps last run's numbers, while an explicit `null` is shown as `n/a`). The rewrite runs even when the measuring or the upload failed (that failure still fails the job), but not after a failed checkout of the app or of fleet (`if: ${{ !cancelled() && steps.app.outcome == 'success' && steps.fleet.outcome == 'success' }}`), and the report's text in the job summary leaves the section out, since `loop-stats`' own Markdown is there. Without `--stats` the report is unchanged. `tests/test_loop_stats.py`, additions to `tests/test_review_mine.py`, and the self-test case `review-mining-artifact`, which checks the dry run's artifact.
- Ticked report rows become Agent task issues (`FLEET-MINING-TASKS`): `.github/workflows/mining-tasks.yml` (`workflow_call`; the caller triggers it on `issues: [edited]`; inputs `dry-run`, `fixture` (self-test only) and `fleet-ref`; `issues: write` only, no secrets; concurrency `mining-tasks-<issue>`, never cancelled) runs only for an edit by the repository's owner of a `review-mining` issue opened by `github-actions[bot]`, and `fleet mining-tasks --event PATH` checks the same again. Each run re-reads the report and opens one issue per row that is ticked and links no issue yet (at most 20 per run), so a tick whose run was dropped by the concurrency group or whose issue failed to open is picked up by the next edit, and a tick withdrawn before the run opens nothing; titled by table (`Check for "<kind>"`, `Review guidance for "<kind>"`, `Findings left open at merge: "<kind>"`, `Verification gap: <area>`), in the agent-task shape (Context with the row's cells defused and a link to the report, Scope from the row's proposal, Out of scope, Acceptance criteria, Tests, Depends on, Model: Fable for review guidance, Opus otherwise), label `review-mining`, no assignee, ending with a hidden `<!-- mined-from row:<id> -->`; then, after reading the report once more, writes ` → #N` at the end of the row's checkbox line on that freshest body. A row whose marker is already on a bot-opened `review-mining` issue (open or closed) is linked to it instead, so the same event twice opens nothing new; unticking or re-ticking a linked row does nothing. `fleet review-mine` keeps those ticks and links across its rewrites, as before, and now also lists the `review-mining` issues (open and closed) to put back the ` → #N` and tick of a row whose `mined-from` marker is on a bot-opened issue, so a link lost to the two writers overlapping (they share no concurrency group, so an edit can't drop the scheduled report) comes back. The self-test runs it in dry run on `tests/fixtures/events/mining-tasks-tick.json`; the security fake `gh` answers a `{"__series__": [...]}` entry one item per call.

### Changed

- `tools/fleet` runs fleet by commit, not by tag: `.fleet/version` keeps the version on line 1 and gains, on line 2, the 40-hex commit that tag points at, and the shim runs `uvx --from "git+https://github.com/AnthonyPluth/fleet@<commit>"`. A missing or malformed commit is an error naming the `fleet sync` that writes it, never a fallback to the tag. `fleet sync --to vX.Y.Z` takes the commit from the workflow pins at that version (`@<commit>   # vX.Y.Z`), else from `git ls-remote` of the tag, or from `--commit <sha>` (which must match the pins), so the sync pull request after a Dependabot bump writes the commit Dependabot pinned; pins at one version naming two commits, or any pin at that version by a ref that can move (`@main`, a tag), are refused. `fleet drift` fails on a missing (from this version on; v1.0.0 content wrote none and still passes), malformed or extra line, and on a commit other than the one the pins at that version name. `sync.yml` plans with the pins' commit (the plan's new `commit` output; pins moved to another commit at the content's version plan a sync, not `none`) and fails when the tag it clones isn't at that commit; the migration issue's command names the commit too. `fleet loop-stats` reads the version from line 1. `fleet self-check` fails on a docs snippet that fetches fleet at a tag or branch rather than `@<commit>`, and the adoption steps now run the first `fleet sync` through `uvx` at the pins' commit (it vendors `tools/fleet` and writes `.fleet/version`; no more `echo` or `curl`). The Claude Code marketplace in `.claude/settings.json` stays at the tag: its `ref` takes a branch or tag, not a commit. Nothing to change in an app: the next sync pull request (or `fleet sync --to <new version>` by hand) regenerates `tools/fleet` and `.fleet/version` together; an app's own script that reads `.fleet/version` whole should read its first line.
